## 2. Recheck mutation preconditions from current state under the lock

In a deterministic interleaving, inject an in_progress T1 state just as the approval lock is acquired: approval exits 0 and the newly active task disappears from saved state. This violates the active-task rejection rule and loses workflow data.

Start rechecks OTHER active tasks under lock but not whether this SAME task already started after its initial read. In a deterministic interleaving, invoke a successful inner start T1 immediately before the outer start acquires its mutation lock. Both exit 0; the ledger contains start attempt 1 followed by start attempt 2 without any triage.

Under the mutation lock, reload state and revalidate approval/task identity and relevant attempt preconditions before saving. Refuse stale operations rather than overwriting newer state or advancing attempts. Approval must preserve every task entry and reject a task that became active during its wait. Start must reject when that task's status/attempt/start lineage changed during baseline work. Revalidate the approval/card/config binding used for the start, so a queued operation cannot stamp an older epoch after a concurrent reapproval.

Add deterministic lock-boundary regressions for both reproduced interleavings; no parallel builds/test suites or unreliable sleeps are necessary. The test may inject a valid state transition at lock entry, and the duplicate-start test can call a real inner start before allowing the outer lock acquisition. Keep successful ordinary start/approve controls.
