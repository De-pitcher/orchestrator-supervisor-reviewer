## 2. Completion manifest (`osr.completion.v1`)

Stored as the `done` entry's `data["completion"]` and mirrored at
`state.tasks[T].completion`. Canonical JSON is `sort_keys=True,
separators=(",", ":")`; all digests are SHA-256 of raw UTF-8 bytes.

| field | type | meaning |
|---|---|---|
| `schema` | str | exactly `"osr.completion.v1"` |
| `task` / `attempt` | str / int | must equal the `done` entry |
| `approval_epoch` | int | ledger seq of the newest `plan_approved` entry |
| `plan_sha` | hex | **raw bytes** of `.ai/PLAN.md` (distinct from the normalised `plan_hash`) |
| `config_sha` | hex | canonical-JSON `sha_config()`, never raw config bytes |
| `ignore_sha` | hex | digest of the sorted governed ignore list |
| `card_sha` | hex | **raw bytes** of `.ai/tasks/<task>.md` (cards live in ignored `.ai`) |
| `inputs_sha` | hex | `input_hash(card)`; traceability only, never compared byte-for-byte |
| `start_seq` | int | ledger seq of the task's `start` entry |
| `start_base_sha` | hex or null | digest of the running accepted map at start; `null` only for a legacy epoch |
| `start_snapshot_sha` | hex | digest of the start snapshot map (`path -> sha`) |
| `verified_fp` | hex | `data.fp` of the referenced passing verify |
| `verify_seq` | int | that verify's ledger seq |
| `spec_review_seq` / `quality_review_seq` | int | the two PASS reviews' seqs |
| `delta` | object | `{path: sha}` for add/modify, `{path: null}` for delete, relative to the start snapshot |
| `result_sha` | hex | canonical digest of the map after applying `delta` |
| `path_count` | int | delta length (truncation defence) |

Approval state (`st["freshness"]`, written by `approve-plan` under the existing
ledger lock): `{epoch, plan_hash, plan_raw_sha, config_sha, ignore_sha,
manifest: {path: sha}, manifest_sha}`. The ledger `plan_approved` record carries
`approval_epoch`, `plan_raw_sha`, `ignore_sha` and `manifest_sha` (the full
manifest is not duplicated there). The ledger commitment is the approval anchor:
re-signing only the state manifest and its self-digest cannot redefine the
human-approved baseline.

## 3. Acceptance algorithm (`evaluate_acceptance`)

One evaluator drives reporting `audit` and read-only `audit --check`. Verdicts:
`0` clean, `1` FAIL (proven stale/malformed/laundered), `2` UNVERIFIED/pending.

1. **Integrity first.** Ledger chain and anchor are verified before any other
   check.
2. **Approval binding.** Newest `plan_approved` defines the epoch. The ledger
   baseline keys must be complete or absent; a partial commitment fails closed.
   With a baseline, `state.freshness`, the ledger record, the current raw
   `PLAN.md` bytes, the canonical config and the ignore policy must agree.
   Missing state with a ledger baseline, or state with no ledger binding, fails
   closed — there is no automatic adoption. The normalised `plan_hash` and
   canonical `config_hash` contracts are preserved and checked separately from
   the raw plan/card digests. `approve-plan` refuses to establish an epoch while
   any task is `in_progress`; active work is never rebased silently.
3. **Baseline.** No ledger baseline and no state baseline = legacy epoch. A
   completion there may be internally valid but is always UNVERIFIED and gets
   no current requirement credit.
4. **Chronological replay.** Valid `done` deltas are replayed in completion
   order into a running accepted map, seeded with the approval baseline (or the
   recorded start snapshot for a legacy epoch). For each record:
   - state `done` and a matching ledger `done` must both exist; state-only,
     ledger-only and duplicated records are FAIL;
   - missing completion metadata is UNVERIFIED in a legacy epoch and FAIL in a
     baseline epoch; malformed new-format records are FAIL;
   - state and ledger completion mirrors must be equal; `audit` never repairs a
     counterpart;
   - schema/types, task/attempt, epoch, raw plan/card, config and ignore must
     match current bytes; `start < verify < spec < quality < done` for this task,
     with all three seqs naming this attempt's records and carrying the same
     `start_seq`;
   - the `start` event must carry the same card, snapshot and base digests;
     the snapshot file must still match its recorded digest;
   - every delta path must be inside the recorded card scope; delete is explicit
     `null`; `result_sha` and `path_count` must describe the applied delta;
   - the work fingerprint is recomputed from the *actual* delta and result map
     and must equal `verified_fp`; the referenced verify and both reviews must
     report that same fingerprint;
   - at a baseline epoch, `start_base_sha` and `start_snapshot_sha` must both
     equal the running accepted map, which rejects pre-start drift.
5. **Compare the final tree once.** Only after replay is the final accepted map
   compared with `walk_tree(cfg)`; add/modify/delete names the path and the task
   that last accepted it. Ignored cache writes stay green.
6. **Requirement rows.** VERIFIED requires an accepted (non-legacy) completion
   and a spec review bound to that accepted attempt. Legacy/unverified evidence
   surfaces as UNVERIFIED, never as credit.
7. **Read-only audit.** `audit --check` prints the same verdict and writes
   nothing: no `AUDIT.md`, state, ledger, log or command execution. Reporting
   `audit` differs only by writing `.ai/AUDIT.md`.

Related gates:

- `start`: derive the accepted map first; reject a non-legacy tree that differs.
  A legacy epoch records `start_base_sha: null` and warns. Reject a second
  `in_progress` task, checked again under the mutation lock against current
  state. Bind card/snapshot/base/plan/config/ignore/epoch in the start event and
  state.
- `verify`: snapshot the governed map before and after the commands and compare
  governed content, not only scope. Any change records `ok=False` with the
  stable-rerun diagnostic; only a run that observes the final tree passes.
- `review`: require the current verify fingerprint and `start_seq`.
- `done`: rebuild the delta from the recorded start snapshot, reject a changed
  card (scope expansion), require the epoch and verify/review lineage, then write
  the completion mirror and `done` record under the ledger lock. That is not a
  multi-file transaction; any half-write is FAIL at audit and is never repaired.
