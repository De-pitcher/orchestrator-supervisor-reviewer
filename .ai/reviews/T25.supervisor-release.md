Decision: red reproduction accepted; implementation is released ONLY with the contract amendments below. No additional red checkpoint is needed for the specified regression additions. This is not a formal spec/quality PASS or completion.

## 1. Replay historical versions, then compare the final tree once
Reject the proposed step that compares EVERY historical delta value with today's file bytes. T1 may accept a.py hash H1 and T2 may legitimately supersede it with H2, including deletion and later recreation. T1's H1 must be checked against its historical verification, not against current H2.

Replay valid deltas in completion order into the running accepted map. Check each delta's scope and internal bindings; verify its result_sha against that intermediate map. Only after replay compare the final accepted map with current governed bytes. Existing sequential-overlap controls must remain green. Add legitimate add/delete/recreate controls; use the existing explicit deletion waiver in the throwaway fixture if the static gate requires one, rather than disabling static checks.

Separate acceptance-lineage derivation from the final audit verdict. Todo tasks, a current active task and pending human requirements may make the final audit incomplete but must not prevent deriving the last accepted map for start. Done validates the active task's candidate delta against its start base before comparing its candidate result with the current tree. Do not reject implementation simply because its intended active delta differs from the previous accepted map.

## 2. Bind the approval baseline into the ledger
The state freshness block alone is not an approval anchor: changing its manifest and self-reported digest together must not redefine the human-approved baseline.

Retain the proposed state block, but add its manifest digest, ignore-policy digest and raw plan/card representation commitments as applicable to the actual plan_approved ledger record. Compute/write the epoch under the existing lock so state and the specific approval entry agree. A baseline missing from one side, mismatched digest/epoch or partial write fails closed; no automatic adoption.

Preserve the existing normalized plan_hash/config_hash contracts for compatibility. If completion plan_sha/card_sha are raw-byte hashes as proposed, store/check those raw representations explicitly and consistently; do not compare a CRLF raw-byte plan digest to the existing read_text-normalized plan_hash. sha_config remains canonical JSON, not raw config bytes. Add a Windows/newline-compatible approval-binding control and a state-baseline-tamper test that recomputes the state's own digest while leaving the approval ledger commitment untouched.

## 3. Bind completion to the actual start and verified delta
Add start_seq to the completion schema. Task/attempt alone is insufficient because reset can reuse attempt 1. Require start < verify < spec review < quality review < done for the same task, start lineage and approval epoch. Bind the start snapshot digest, base digest and card digest in the start event/state. A card changed during the task must not silently expand its originally recorded scope.

For a baseline-backed epoch, require the start snapshot map to equal the running accepted map at that start. Derive the completion delta from the recorded start snapshot and candidate result, with explicit null deletions. Recompute the existing work fingerprint from that actual delta and result hashes, and compare it with the referenced verify/review fp. Merely copying verified_fp into a new manifest and checking scope/result_sha is not proof that the manifest describes the verified bytes. Require state/ledger completion mirrors to agree; never repair missing counterparts during audit.

Scope chronological replay to relevant current task lineages, rejecting a reused current card with old-epoch completion as stale. Preserve and disclose unrelated archived task history without letting it supply current requirement credit or permanently poison a new workflow. Do not replay every old reset attempt as an additional current completion.

## 4. Correct two fixture defects before implementation
The proposed stability test currently writes a.py BEFORE start, violating the very new pre-start rule it intends to test. Also its mutating runner already writes the final value during the start baseline, so a later verify may perform no observable change.

Make the fixture runner mutate only when an explicit throwaway .ai marker is present. Complete start with that marker absent and the approved bytes unchanged. Create the marker AFTER start, then verify: a.py changes during the run, verify records ok=False with a stability diagnostic. A rerun on the now-stable bytes must succeed. Keep the original failure assertions and add this stable-rerun control; do not weaken the pre-start guard to accommodate the fixture.

The proposed legacy test appends a metadata-free done after a new-format completion. After implementation that is a conflicting/interrupted new record, not authentic legacy evidence. Keep that conflicting-record rejection case, but build a separate genuine old-format fixture with an old-style approval, no freshness block and no completion metadata on either side. Its chain remains readable and its audit is UNVERIFIED/nonzero. A malformed new-format record or state/ledger mismatch is FAIL, not automatically downgraded to legacy. Tests may deliberately seed historical fixtures; production must never manufacture past approvals.

## 5. Minimal additional adversarial coverage
Before green submission cover: legitimate addition/deletion/recreation; state-baseline mutation with a recomputed self-digest; mismatched start/verify fingerprint bindings; both state-only and ledger-only interrupted completion writes; a second active start rejection; changed card during an attempt; and audit --check preserving ALL project file bytes (not just .ai) on both clean and stale outcomes. Extend existing tests where the scenario naturally fits. No tests whose only oracle is matching implementation source strings.

Use existing lock conventions without claiming multi-file atomicity. Check single-active-task state again under the mutation lock using current state, not an old unlocked snapshot. No parallel builds or test suites are needed.

## 6. Legacy transition: no automatic promotion or live migration in T25
T25 began under a legacy approval without a baseline. Record that lineage honestly; its completion may be UNVERIFIED for final acceptance while the task's verify and independent technical reviews can still pass. Never resnapshot legacy state silently or claim that a new approval makes old task reviews current. Existing current-card old-epoch completions remain stale; missing metadata remains unverified.

After T25 is independently accepted, the supervisor will prepare ONE concrete transition packet before T26: preserve/retire completed old-epoch cards, adjust remaining dependencies explicitly, retain R20-R25 coverage through the fresh integration card, and capture a new baseline through actual human approval. Retired history remains disclosed but is not current requirement credit. If there is an in-progress task, approval must reject or explicitly require its retirement before establishing the new epoch; do not rebase active work silently. Test this behavior. Do not perform that migration, change live cards/config, execute approval/reset, or widen scope during T25.
